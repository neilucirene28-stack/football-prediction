# 竞彩 v13：强度基线候选与来源门控

此次解决的是进球基线的数值定义与证据链。v13默认保留v12数值策略；新规范基线是显式研究候选。没有完成真实赛果的时序校准，不宣称准确率提高，尚未部署或同步至MUSE。伤停、外援、红黄牌的学习系数保持未启用。

## 两种进球基线

旧算法把联赛参考值G除以二，主队再乘H=1.12。球队强度回到1时，主客基线之和为G×(1+H)/2；G=2.7时是2.862球。历史主客场进球也按G/2归一化，主场差异可能再进入H。

新候选用主队基线G×H/(1+H)、客队基线G/(1+H)。历史主场进球按主场基线、失球按客场基线归一，客场相反，中性或未知场地明确诊断并用G/2。目标中立比赛两队基线各G/2；历史主客场的归一化仍使用固定历史比例1.12。所有已有收缩、衰减、级别、让平和lambda边界数值保留，没有拟合新的系数。

| 配置 | 行为 | 当前用途 |
|---|---|---|
| `strength_baseline_mode="legacy_v12"` | 默认，保留现行基线与浮点运算顺序 | 现行计算兼容；不自动应用候选联赛统计 |
| `strength_baseline_mode="venue_normalized"` | 主客场基线相加等于输入总均值 | 独立研究比较；未经真实赛果验证 |
| `league_min_matches=30` | 全联赛统计的最少支持场数 | 证据门槛，尚未按赛果校准 |

候选不是通过强行选择3-2、4-1来制造多样性。lambda上下界、赔率融合、让平矩阵调整仍可使最终矩阵期望偏离基础输入均值；这部分有独立诊断，不能把基线相加恒等式当成整套模型均值无偏证明。

## 全联赛统计契约

可选输入 `league_statistics` 的schema为 `jingcai.league-statistics.v1`。必需字段包括：

| 字段 | 含义 |
|---|---|
| `source`, `competition_id`, `season_id`, `phase_id` | 明确的同源原生赛事、赛季、阶段标识 |
| `match_count`, `home_goals`, `away_goals` | 全联赛已完成比赛的整数汇总 |
| `sample_scope="all_completed_league_fixtures"` | 不是挑选两队的近期样本 |
| `coverage_status="complete_as_of"` | 声明覆盖统计截止前该范围内的全部已完成比赛 |
| `feature_as_of`, `available_at` | 带时区；均不得晚于输入快照 |
| `evidence_sha256` | 原响应64位字节摘要 |

`match_source_context` 必须给出与统计一致的上述四个身份字段。不能跨来源、赛季或阶段合并；阶段未知不自动补全。达到最少场数后，候选使用(主队进球+客队进球)/场数。与明确传入的 `league_avg_goals` 冲突时拒绝候选，避免两个基线来源互相覆盖。默认兼容模式只记录符合条件的观测值，不自动启用。

引擎校验调用方声明的身份、数值、时间与摘要格式；它不联网认证来源，摘要格式通过也不代表已经逐字节核对原件。正式采集或导入仍须保存原响应并核对真实摘要、统计覆盖和原生身份。审计明确标为 `caller_declared_not_source_authenticated`。

本轮22场原输入没有这种全联赛统计，全部保留“2.7为模型默认、不是观测均值”的标记。不得用主客两队的近期比赛平均值冒充全联赛统计。

## 历史对手评级契约

裸 `opp_attack` / `opp_defense` 数字缺少原生身份与时间范围，在新竞彩入口不参与数值修正。新增 `opponent_strength` 对象需有 `source`, `team_id`, `attack`, `defense`, `sample_matches`, `feature_as_of`, `available_at`。

评级来源、team_id必须与该历史行的source、opponent_id一致；scale为 `relative_to_league_venue_baseline`，sample_scope为 `strictly_before_historical_match`。评级特征截止必须早于那场历史比赛开始；可在本次快照前采集，但不能把该历史比赛之后形成的对手表现回填到该场修正。只知道完赛时间不能证明赛前窗口。未知身份或尺度保留排除理由，未来信息直接拒绝。

这只是证据门控，不代表已为真实球队采集或训练对手评级。默认模式对无证据裸值的处理会与旧调用不同；输入方需要补充明确证据，不能保留虚假覆盖率。旧双模式核心的直接调用维持旧接口行为，生产竞彩必须通过 `engine.jingcai_predictor.predict`。

## 验证与22场结果

核心704项通过，1项缺少psycopg的数据库检查跳过，1项其他项目分支排除；采集器70项通过。合成用例只用于数学不变量、门控、兼容和非修改性验证，不作为准确率数据。

2026-10-11的22场真实赛前输入做三路只读比较：原v12重放、v13默认兼容模式、v13规范基线候选。前两者的完整比分矩阵、胜平负与进球强度逐场等于封存记录。新计算全部标为historical_replay，实际计算时间保留，未新增或改写赛前预测。

候选的预期总进球范围从1.83—4.79变为1.72—4.42；1-1众数从7场变10场；胜平负首选只在012改变，单项概率最大变化3.73个百分点。这个结果支持单独研究，不能证明候选更好；所以未自动改为默认。修复单点众数呈现仍需展示总体比分概率与总进球区间。

原输入JSON、原预测包与22个封存文件共24个文件的字节摘要在比较前后相同。旧通用strengths、旧双模式核心及其他项目源码共23个文件保持字节一致。

包内 `verification/saved_22_input_comparison.md` 为逐场表，JSON包含候选的完整研究结果；`scripts/compare_jingcai_strength_versions.py` 可复现。命令：

```bash
python3 scripts/compare_jingcai_strength_versions.py \
  --records /原始预测目录/predictions.json \
  --reference-project /已核验的v12项目目录 \
  --output /新的研究输出目录
```

脚本自动开启候选参数，保留原配置作参考，要求原目录有22个实际封存文件。它不写原输入目录，不调用实时赛前封存，也不拉取赛后数据。
